# Source-of-truth evaluation: does NetBox stay?

**Date:** 2026-08-08
**Status:** Open question — decision deferred to a fresh session
**Trigger:** Attempting to put `dnstonetbox` live during the `risei.net` → `int.risei.net` migration

## The actual goal

> DNS and DHCP config generated from a versioned source of truth, instead of hand-edited on infra2.

NetBox is one way to reach that, not the goal itself. Restating it this way is what opened the question below.

## Why this stalled

`dnstonetbox` could not simply be pointed at the live zones. Its NSD forward template emits **only** SOA, NS, A, and AAAA, and it writes whole zone files with a `; Generated by dnstonetbox — do not edit manually` header.

Pointing it at `/var/nsd/zones/master/int.risei.zone` today would delete:

- 9 CNAMEs — `vault`, `ldap`, `ai`, `time`, `s3`, `netboot`, `rmq-labs`, `syslog`, `git`
- the `$ORIGIN labs.int.risei.net.` sub-block (mq01, mq02, podagent, srbrain1, sema1)
- `TXT` records on the phone/laptop entries
- in `risei.zone`: the `MX` records and the `_tcp` SRV block

NetBox IPAM cannot model any of those. It has `dns_name` on an IP address and nothing else.

## What drives the re-evaluation

Stated 2026-08-08, in the operator's own priority:

1. **Too heavy for the lab** — PostgreSQL + Redis + gunicorn + Django to track ~20 hosts. Operational weight and upgrade burden out of proportion to the problem.
2. **Data entry burden** — keeping NetBox matching reality is manual and drifts. This is what stalled the project.
3. **Due diligence** — confirming NetBox is still the right choice before investing more build effort.

Explicitly **not** chosen: "poor fit for DNS/DHCP specifically." The DNS gap is not the real pain.

**The key reframe:** drift is not a NetBox flaw. It is inherent to any hand-maintained source of truth. Swapping NetBox for another database with a nicer UI produces a different place to forget to update. The fix is either automatic reconciliation, or a source of truth cheap enough to edit that it stays current.

## Facts established (verified 2026-08-08, no need to re-derive)

**NetBox install**
- Version **4.6.5**, installed from **FreeBSD pkg** (`netbox-4.6.5`); pkg has 4.6.7 available.
- Runs under system **python3.12** via gunicorn, user `www`. **No venv.**
- `PLUGINS = []` at `configuration.py:203`.
- FreeBSD ports has `py312-netbox-secrets` — so plugins *can* be packaged — but there is **no `netbox-dns` port**.
- Consequence: any pip-installed plugin lands in pkg-owned system site-packages and can be clobbered by `pkg upgrade`. A venv created with `--system-site-packages`, with gunicorn run from it, would fix this without a full source install.

**netbox-plugin-dns (peteeckel)**
- Documented compatibility matrix stops at **NetBox 4.5** (plugin 1.5). 4.6.5 is **not** listed.
- Release 1.5.7 notes "adjustments for compatibility with NetBox 4.6-beta1"; a 1.6 beta line exists. So 4.6 support is real but unblessed — **must be validated, not assumed.**
- Requires Python 3.12+ (satisfied).
- Has **IPAM DNSsync**: auto-creates DNS records from IPAM IPs with `dns_name` set. Directly attacks the data-entry burden — existing IPAM data becomes DNS records automatically, leaving only the ~12 records IPAM cannot express to enter by hand.

**Environment**
- `testng` and `testng2` jails exist — the right place to spike a plugin against 4.6.5.
- `genptr.sh` in `/var/nsd/zones/master/` is one-off scaffolding from the migration. Never used automatically, nothing to preserve.
- NetBox is load-bearing beyond IPAM: Ansible dynamic inventory, device/jail records, a `diskless_arch` custom field driving DHCP netboot options, and secrets rendered by a Vault Agent.

**dnstonetbox**
- Direction is **NetBox → DNS config**, despite the name.
- Generators (NSD, Unbound, dhcpd), `WriteIfChanged` atomic writes, unified-diff dry-run, and per-service reload-on-change are all **source-agnostic**. Only `netbox/` binds it to NetBox.

## Options

### A. Retire NetBox; host data as YAML in git

One `hosts.yaml` — name, IPs, MAC, aliases, netboot arch — rendered by `dnstonetbox` reading a file instead of an API. That file is also an Ansible inventory natively.

- **Deletes:** PostgreSQL, Redis, gunicorn, Django, the plugin question, NetBox upgrades.
- **Data entry becomes** a reviewable diff with git history and blame.
- **Preserves** the bulk of `dnstonetbox` — only the `netbox/` package is replaced.
- **Scale check:** ~20 hosts is roughly 150 lines of YAML.
- **Loses:** web UI; next-available-IP allocation; the relational model (device ↔ interface ↔ IP); audit log with attribution (git history covers this for a single operator).
- **Migration cost:** rewrite Ansible dynamic inventory as static; move `diskless_arch` into the YAML.

### B. Keep NetBox; attack the drift

Accept the weight. Add reconciliation that reads reality (`jls`, DHCP leases, zone files) and reports what NetBox is missing. Optionally still adopt netbox-dns for record modelling.

- Right if the UI, next-free-IP allocation, and relationship modelling are worth their operational cost.
- Does **not** address "too heavy."
- Still needs the plugin spike, the venv hardening, and a `dnstonetbox` rework to read plugin records.

### C. Infrahub or another platform

More capable than NetBox, models DNS natively, from the same people behind NetBox.

- Strictly **heavier**, which is the opposite of the stated pain. Listed for completeness; not recommended on current evidence.

## Recommendation

**Option A**, on the evidence. Two of the three stated drivers are weight and data-entry burden, and A is the only option that reduces both. It also preserves most of `dnstonetbox` rather than discarding it.

The counter-argument worth taking seriously: NetBox is already integrated with Ansible and Vault, so retiring it is not free, and "I know the creators" is a legitimate reason to stay in an ecosystem.

## Open questions for the next session

1. **Is drift solved by direction?** If configs are *generated* from the source of truth, drift cannot occur in that direction. What still needs reconciling — DHCP leases for unmanaged devices? New jails?
2. **What else consumes NetBox** beyond Ansible inventory and `diskless_arch`? A full consumer inventory decides the true migration cost. (Compare with the Vault client enumeration done via audit log on 2026-08-08 — enumerate empirically, not from memory.)
3. **Does the phone/laptop data belong in a source of truth at all?** `ipocalypse`, `angelfish`, `neontetra` etc. are DHCP clients with TXT comments. They may be better served by dynamic DHCP than by static records anywhere.
4. **If A: what is the reconciliation check?** Something that reads live zones/leases and reports divergence from `hosts.yaml`, so drift is *detected* even though generation is one-way.
5. **If B: run the plugin spike first.** netbox-dns on `testng` against NetBox 4.6.5 — does it install, migrate, and run? That single question can invalidate the whole B path, and it is cheap.

## Not in scope

The `int.risei.net` migration itself is complete for the Vault tier. Leaf services (`grafana`, `prom`, `loki`, `alertman`, `s3`, `pgdb1`, `imap01`) have not moved and need their own plan — see the vaultjails repo. Whatever is decided here should land **before** those hostnames move, so the rename happens once, in whatever the new source of truth turns out to be.
